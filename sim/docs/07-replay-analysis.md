# 分析项目：原始算法复算 vs Gazebo 实测

目标：把「上游原始算法（`UAV_Control`）」和「仿真里实际跑出来的轨迹」放在一起比，
用来回答两个问题：

1. 我们现在发出的指令，是否等于**原始算法**在同样状态、同样参考下的输出？
2. 如果让原始算法驱动一个理想双积分器，它会不会走出 Gazebo 里那条轨迹？
   —— 差距来自算法本身，还是来自被控对象/内环/延迟？

## 工具

| 脚本 | 作用 |
|---|---|
| `scripts/28_traj_record.py` | 逐拍记录控制器内部量到 CSV：状态、参考位置/速度、加速度指令、阶段、真值 |
| `scripts/29_replay_original.py` | 用原始 LQR 复算指令，并做**闭环重放**（理想双积分器 + 记录的参考），与 Gazebo 轨迹对比 |

一键采集：

```bash
cd sim && ./scripts/16_moving_landing_demo.sh --no-gui --no-record --traj --timeout 90
python3 scripts/29_replay_original.py --csv logs/traj-<时间戳>.csv --outdir logs/replay
```

## 第一次结果（2026-11-06，移动平台着陆，真值参考）

```
样本 820 拍（只取 LQR 接管的 transit/approach/descend/settle），时长 54.3 s
[指令] 原始算法 vs 我们发出的：RMS 2.45 m/s²，最大 3.97
[轨迹] 原始算法闭环 vs Gazebo：末端 0.67 m，最大 8.47 m（出现在转场起始段）
```

## 已看出的两个问题

### 1. 转场 → 进场时，参考高度有 **10 m 阶跃**

右上图（vertical）里绿色虚线在 t≈24 s 从 −10 m 直接跳到 0 m——
这是阶段切换时 `z_offset` 从 `-cruise_alt` 变成 `-clearance` 造成的**瞬时阶跃**。

后果：飞机只能靠 LQR 去追这个阶跃，表现为"突然俯冲"。这在实机上很危险
（近船、近水面），应该改成**限速的高度剖面**（例如 0.5 m/s 线性下降）。

### 2. 指令复算的 RMS 2.45 m/s² 偏大

可能原因（按可能性排序）：

1. **增益调度没复现**：节点每次 `_update_gains()` 会用平台速度与横向方向重建增益，
   重放脚本固定用 `(0,1,0)` 且只在阶段切换时重建
2. **曲率预览没复现**：`curvature_preview` 没有记录进 CSV，重放时按 0 处理，
   而实际运行时启用了 `curvature_weight=1e-3` 的前馈
3. **记录频率**：CSV 是 20 Hz 采样，控制器实际更快，采样点之间的指令变化看不到
